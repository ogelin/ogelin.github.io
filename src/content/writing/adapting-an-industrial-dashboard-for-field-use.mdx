As I’m wrapping up my work at Teledyne, I’ve been thinking about the challenges of adapting a legacy dashboard for reviewing instrument readings on a mobile device in the field.

Initially, the desktop product had two levels of informational pages: a dashboard of compact widgets and detailed pages with a richer, interactive version of each widget. For instance, a detailed page could include filters, results, a selected item for context, time-series instrument readings, a chart, and a map, in addition to the content from the overview-level dashboard.

My goal was to drive a newer, mobile-friendly version of the application intended for users in the field who might, for example, be checking a reading while handling equipment. It needed to be easy to use in a simplified format while preserving the functionality, data, and workflows that users already knew well.

I took the occasion to rework the data visualization, not only to make it more mobile-friendly, but also to make it more readable by avoiding several y-axes in one plotting area. The desktop keeps the initial design because users were familiar with the legacy version. The newer mobile design splits the series into stacked charts with a shared x-axis and separate y-axes.

The mobile design also reuses the table headers as the legend to make better use of the reduced space. Selecting a row aligns the same timestamp across all three series. Switching to the Neighborhood Map changes the upper view but keeps the selected row and table in place. This gives the trends, readings, and Neighborhood Map their own focused views while preserving context.

## Separating the layers inside a widget

On desktop, Session Data behaved like a dashboard. The filter form, result table, selected-session summary, readings, chart, and map could all be visible at once, and their selections formed the context that led to interdependent updates across the sections.

On mobile, the same material was divided into a multi-step flow with context:

This introduced navigation state that the desktop layout did not need. The submitted search and its results had to remain available while someone moved deeper into a session. Back returned to the previous screen with that context intact. A new search replaced the result set and cleared the old selection.

```text
submitSearch(filters):
  context = { filters, results: search(filters), selected: null }
  view = "results"

openResult(session):
  context.selected = session
  view = "summary"

back():
  view = previousView(view)   // context remains available
```

## When migrations in a legacy codebase collide

The responsive work was added while the application was also moving to a newer Angular version and a newer PrimeNG component library. The PrimeNG migration was motivated in part by WCAG 2.0 requirements, which I kept in mind while making choices for the mobile experience, including the [W3C guidance on reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html). A reported bug could come from the mobile feature, either migration, or the interaction between them.

Martin Fowler's [Patterns of Legacy Displacement](https://martinfowler.com/articles/patterns-legacy-displacement/) describes the same tension: new requirements keep moving while the underlying technology is being replaced. Here, the harder part was separating framework changes from PrimeNG changes and feature work that were moving at the same time.

Users were attached to the legacy version, so I had to make sure the desktop version kept parity, except for intended PrimeNG changes, even when the mobile work affected shared code.

Before assigning a bug to the mobile work, I checked the same path against the relevant branches and noted where the behaviour first changed. The order of merges mattered because migrated templates and component events could affect the feature, while feature styles could expose a change in PrimeNG. Keeping branches scoped and recording which change belonged where made the regression work more reliable.

I compared the related pages at desktop and mobile widths as those styles were introduced. The goal was for both versions to look like the same product, even though the mobile version used a different sequence of screens.

## Conclusion

The mobile version kept the dashboard’s two-level structure while breaking each detailed workspace into focused views. Persistent filters and selections preserved context as users moved through search, results, summaries, readings, charts, and maps. The chart redesign improved readability on a smaller screen, while desktop parity and regression tracking protected the workflow existing users knew. The broader question is not how to make a desktop product smaller, but how much its structure can change before the relationships that make it useful are lost. Although my immediate goal was to make the application mobile-friendly, coordinating it with the Angular and PrimeNG migrations showed both why the legacy codebase and interface needed to be modernized and that the modernization could be done incrementally.
